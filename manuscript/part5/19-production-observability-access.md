# 19장. 운영 관측 데이터를 Agent에게 열어도 되는가

지금까지는 Agent가 Prometheus, Loki, Tempo, Pyroscope를 직접 조회하는 흐름을 만들었다.

여기서 자연스럽게 다음 질문이 나온다.

> 운영 데이터를 Agent에게 직접 보여줘도 괜찮을까?

기술적으로 가능하다는 것과 운영에서 허용해도 된다는 것은 다른 문제다.

## 1. 기본은 읽기 전용으로 시작한다

첫 단계에서는 Agent가 운영 시스템을 바꿀 이유가 없다.

필요한 것은 대부분 이런 정보다.

- 지표
- 로그
- trace
- profile
- Pod 상태
- 배포 버전

이 단계에서는 read-only 권한으로 충분하다.

## 2. Agent 전용 계정을 쓴다

사람 계정을 공유하지 않는다.

Agent용 service account를 따로 만들고 필요한 datasource와 environment만 허용한다.

예를 들어 production 전체가 아니라 특정 서비스만 보게 할 수 있다.

## 3. 모든 로그를 보여줄 필요는 없다

운영 로그에는 민감한 값이 섞인다.

- Authorization header
- cookie
- 사용자 식별자
- request body
- SQL parameter

이런 값은 Agent 앞에서 숨기는 것이 아니라 가능하면 수집 단계에서부터 제거한다.

## 4. tenant 경계도 지켜야 한다

멀티테넌트 시스템에서는 Agent가 한 고객의 장애를 조사하다가 다른 고객 로그를 읽으면 안 된다.

그래서 service뿐 아니라 tenant scope도 query 조건에 강제로 붙일 수 있어야 한다.

## 5. 조회 비용도 운영 비용이다

Agent가 반복해서 넓은 로그 검색을 하면 Loki나 다른 backend에 부담을 줄 수 있다.

따라서 다음을 제한한다.

- 최대 시간 범위
- 최대 scan 크기
- 최대 결과 수
- query timeout
- 호출 빈도

## 6. 감사 기록을 남긴다

Agent가 어떤 query를 실행했는지 남겨야 한다.

나중에 다음 질문에 답할 수 있어야 한다.

- 어떤 데이터를 봤는가
- 어느 시간대를 조회했는가
- 어떤 범위를 벗어나려 했는가
- 어떤 결과가 잘렸는가

## 7. 외부 LLM을 쓴다면 데이터 경로를 다시 본다

Agent가 SaaS 모델을 사용한다면 관측 데이터가 외부 provider로 전송될 수 있다.

이 경우 허용 범위와 데이터 분류를 다시 검토해야 한다.

필요하다면 원문 대신 요약된 evidence만 보내는 구조를 사용한다.

## 8. 이 장에서 기억할 것

> 운영 관측 권한은 처음부터 최소한으로 준다.

> 읽기 권한, 데이터 범위, query 비용, 민감정보를 각각 따로 통제한다.
