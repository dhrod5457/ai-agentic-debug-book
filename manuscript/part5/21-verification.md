# 21장. 수정했다고 끝난 것이 아니다

Agent가 코드를 수정했다.

테스트도 통과했다.

문제가 해결됐다고 말해도 될까?

아직 한 단계가 남았다.

처음 장애를 확인했던 신호가 실제로 좋아졌는지 봐야 한다.

## 1. 처음 증상으로 돌아간다

DB pool 장애였다면 처음 본 것은 p99와 pending connection이었다.

수정 후 같은 부하에서 다시 본다.

~~~text
Before
p99 3.1s
pending 37

After
p99 240ms
pending 1
~~~

이 비교가 있어야 실제 incident 해결을 말할 수 있다.

## 2. 테스트 통과와 운영 해결은 다르다

단위 테스트는 로직이 맞는지 확인한다.

운영 장애는 latency, resource, concurrency, platform 상태 때문에 생길 수 있다.

그래서 test pass만으로는 부족하다.

## 3. 같은 workload로 다시 확인한다

가능하면 수정 전과 같은 입력과 부하를 사용한다.

조건이 다르면 결과 비교가 어렵다.

## 4. 하나의 숫자만 좋아졌다고 끝내지 않는다

예를 들어 latency는 좋아졌지만 error rate가 늘 수 있다.

그래서 최소한 기능 결과와 장애 신호를 같이 본다.

## 5. 남은 이상도 기록한다

완전히 사라지지 않은 이상이 있다면 숨기지 않는다.

~~~text
p99는 정상화
하지만 GC pause는 여전히 높음
~~~

이런 경우는 부분 해결이다.

## 6. 검증 결과도 다음 디버깅의 자료가 된다

수정 전후 데이터는 다음 장애에서 좋은 참고자료가 된다.

하지만 자동으로 '정답 규칙'으로 만들지는 않는다.

환경과 버전이 달라질 수 있기 때문이다.

## 7. 이 장에서 기억할 것

> 처음 문제를 발견한 신호를 수정 후 다시 본다.

> 테스트 통과와 장애 해결은 같은 말이 아니다.
