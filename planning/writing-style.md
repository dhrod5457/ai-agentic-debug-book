# Writing Style Guide

기준일: 2026-10-05

이 책은 observability와 AI Agent를 처음 함께 다루는 실무 개발자도 부담 없이 읽을 수 있어야 한다.

## 1. 문체

전문 용어를 설명하기 위해 전문 용어를 더 만들지 않는다.

기본 흐름은 다음과 같다.

실제 상황
→ 사람이 평소 어떻게 확인하는가
→ Agent에게 무엇이 빠져 있는가
→ 필요한 구조
→ 그 구조의 이름

용어가 먼저 나오지 않는다.

## 2. 한 문단에 새 용어 하나

가능하면 한 문단에서 여러 새 개념을 동시에 소개하지 않는다.

Bad:
> Correlation ID와 Runtime Identity를 Evidence Envelope에 포함하고 Progressive Narrowing으로 Bounded Retrieval을 수행한다.

Better:
> 먼저 같은 요청에서 나온 로그와 trace를 묶을 수 있어야 한다. 보통 trace ID가 이 역할을 한다. 그 다음에야 Agent가 필요한 로그만 좁혀 볼 수 있다.

## 3. 영어는 필요한 만큼만

실무에서 이미 익숙한 단어는 유지할 수 있다.

- log
- metric
- trace
- span
- profile
- Agent
- API
- SQL
- JVM
- Kubernetes

하지만 새로 만든 설명용 용어는 한글 설명을 먼저 쓴다.

예:
> 문제가 발생한 실행에서 가져온 자료를 이 책에서는 '실행 증거(Runtime Evidence)'라고 부르겠다.

## 4. 정의보다 사례

각 장은 가능한 한 실제 장애 상황에서 시작한다.

예:
- API가 갑자기 3초 느려졌다.
- 배포 직후 500 오류가 늘었다.
- Pod가 재시작되는데 애플리케이션 로그에는 오류가 없다.

긴 정의나 기술 역사로 시작하지 않는다.

## 5. 제품 이름은 주인공이 아니다

Prometheus, Grafana, Loki, Tempo는 문제를 해결하는 예시다.

Bad:
> Tempo는 TraceQL을 제공한다.

Better:
> 느린 요청 하나를 찾았으면 이제 그 요청이 어느 구간에서 시간을 썼는지 봐야 한다. Tempo에서는 이런 작업을 trace 검색으로 할 수 있다.

## 6. 그림과 예시를 자주 쓴다

긴 설명보다 작은 흐름을 사용한다.

~~~text
느린 API
  ↓
지연시간 확인
  ↓
느린 요청 하나 선택
  ↓
관련 로그 확인
  ↓
원인 후보
~~~

도식은 설명을 대신할 수 있을 때만 넣는다.

## 7. 목록 남발 금지

목록은 비교, 체크리스트, 구성요소 정리에만 사용한다.

핵심 논리는 문장으로 설명한다.

## 8. 한 장에서 독자가 가져가야 할 문장

각 장에는 독자가 기억할 문장을 1~2개만 둔다.

예:
> 로그를 많이 주는 것보다 필요한 로그를 찾게 하는 편이 낫다.

## 9. 이 책의 synthesis 용어

다음 표현은 본문에서 최소한으로만 사용한다.

- Runtime Evidence
- Evidence Escalation
- Agent Debug Session Contract
- Bounded Tool Surface

처음 등장할 때 쉬운 한국어 설명을 붙이고 이후에도 가능하면 한국어 표현을 우선한다.

## 10. 장별 기본 구조

현실적인 문제
→ 잘못된 첫 접근
→ 사람이 실제로 확인하는 과정
→ Agent에게 필요한 정보
→ 오픈소스 예시
→ 주의할 점
→ 한 문장 결론

## 11. 난이도 조절

본문은 이해를 우선한다.

세부 API, query 문법, RBAC 세부 설정, schema는 필요하면 별도 박스나 부록 성격으로 밀어낸다.

독자가 본문을 읽기 위해 PromQL, TraceQL, LogQL 문법을 먼저 알아야 해서는 안 된다.

## 12. 검토 질문

각 장을 저장하기 전에 확인한다.

- 이 장을 observability 입문 개발자도 따라갈 수 있는가?
- 첫 3문단 안에 실제 문제 상황이 있는가?
- 새 용어가 너무 많이 등장하지 않는가?
- 제품 설명서처럼 보이지 않는가?
- 한 문장으로 핵심을 설명할 수 있는가?
